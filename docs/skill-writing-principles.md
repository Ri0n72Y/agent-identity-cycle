# Skill 与 Reference 写作原则

Skill 和 Reference 面向高性能 LLM 使用，因此写作重点是提供足够稳定、足够清楚的任务语义，让模型能够结合实际上下文完成判断，而不是用大量机械步骤替代模型自身的推理能力。主 `SKILL.md` 承担能力入口、调用契约和必要路由，Reference 负责描述某类文件中的信息应该怎样存在、怎样被理解以及在同类文件之间怎样变化；涉及不同对象之间的区分和跨层路由时，应优先放在 Skill 中统一处理，避免每一篇 Reference 重复声明整套系统边界。

Reference 应围绕当前文档实际负责的信息展开，直接说明这个对象保存什么、内容怎样写以及信息怎样在该对象内部演化。不要习惯性通过连续的否定句定义对象，也不要为了显得完整而补充与当前文件没有实际关系的边界；如果某个概念的区分已经由上层 Skill 处理，Reference 可以直接使用它而无需再次展开。

优先使用长句、自然段和完整上下文来表达信息，让模型能够看到事实之间的因果、时间和语义关系。标题、列表、代码块和少量内联索引用于帮助阅读与定位，但结构本身不应成为内容的主要载体。对 Memory、Episode、Identity 等长期文本尤其如此：机器检索需要的字段、索引和图关系可以由外部系统派生，人和 Agent 共同维护的 canonical content 应保持可读、可修改、可通过 Git 理解其历史变化。

写作必须以已经发生和已经确认的内容为基础。总结讨论过程时只提炼实际出现过的修改和结论，不为形成一个看似完整的反思而编造此前不存在的错误、理论或修改记录；当已有材料无法支持某个结论时，应让该部分保持未定，而不是用合理化推断填满空缺。

Skill 的复杂度随着真实使用增长。默认保持一个清晰入口，当某条内部流程只是同一能力的一个步骤、并没有独立触发时机和独立存在价值时，优先留在同一个 Skill 中，并在复杂到需要额外上下文时通过 `workflows/`、`references/` 或脚本按需展开。只有当两个过程已经拥有明显不同的调用频率、触发主体、上下文成本或失败边界，并且能够独立完成有意义的工作时，才值得拆成独立 Skill。

`short-memory-appending` 与 `reflection` 的拆分就是这种情况：前者接近每次实质交互后的轻量维护，只写一条近期行动与状态转移；后者需要读取更多历史并判断哪些内容值得进入更慢结构，可以由 Agent 延后、由用户显式触发或由周期任务运行。二者共享同一长期架构，但不应为了保持“一个 Skill”而强迫高频轻操作每次都携带慢速 Reflection 的上下文。

当 Harness 支持 Subagent，并且一项维护工作需要读取较多历史文件、修改多个长期文档或执行与用户当前任务相对独立的整理时，优先考虑把它委派给短生命周期子代理。父 Agent 只提供必要事实、目标路径和判断边界，并接收简短结果或冲突摘要，从而把 Working Context 留给当前交互本身。Subagent 是上下文管理手段，不应成为额外的语义层，也不应因为使用子代理而改变目标文件的格式或归档原则。

Reference、Workflow、Script 等资源只有在存在明确运行价值时才新增，不预先建立空目录或完整模板。文件位置如果属于整个 Skill 的运行契约，应直接写在对应 `SKILL.md` 中；Reference 只保存目标内容自身的整理规则，避免为了记录目录结构再制造一层间接说明。

这套原则本身也属于可演化的 Procedural Knowledge。后续真实 Agent 实践如果反复暴露新的写作、路由或上下文问题，可以修改本文和对应 Skill，并通过 Git 历史保留为什么发生变化，而不把一次性的偏好或单次失败立即提升成普遍规则。
