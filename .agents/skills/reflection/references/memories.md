# Memory整理原则

## Purpose

Memory 保存 Agent 在跨上下文、跨项目工作时仍然需要保持连续性的个性化信息。当前 Memory 维护 Short-term Memory、Long-term Memory 与项目状态记忆，它们分别承担近期连续性、长期个性化理解和动态项目恢复。

## Short-term Memory

Short-term Memory 保存固定周期内每个项目、每个会话最近的状态与最近动作。每次完整的“用户交互 → Agent 实践”结束以后写入一次，正文集中记录两件事：本轮我做了哪些值得留下的行动，以及这些行动结束以后项目或会话状态发生了什么转移。

Short 使用 [标准记忆格式](memory-format.md)：

```markdown
[2026-01-15][project-alpha][20:20]<implementation>

本轮检查了现有实现并完成一处必要修改，验证结果符合预期。当前工作已经从问题定位推进到修改完成，下一轮可以直接进入剩余验证。
```

Short 本身就是一次完整实践后的高度凝练内容，不随每次工具调用持续追加。它只保留固定周期内仍然活跃的项目和会话；超过固定周期且已经不活跃的内容在 Reflection 中完成必要归档后被移除，没有长期价值的近期状态直接退出 active memory。

## Long-term Memory

Long-term Memory 保存跨上下文仍然需要知道的用户与环境信息，并形成一份完整、可读、经过组织的个性化文档。它主要回答：未来面对这个用户和他的工作时，我应该提前知道什么？

内容可以包括用户身份与背景、长期习惯、工作方式、偏好、长期关系、经常涉及的领域以及对未来协作有价值的上下文。它应当保持标题、自然段、少量列表与链接等轻量内联结构，使整个文档能够被直接阅读和理解，而不是按时间不断追加零散事实。

长期项目可以作为用户长期背景的一部分被提及，但具体阶段、最近进度和当前入口统一维护在 `memories/projects.md`。Long-term Memory 只需要知道项目存在、其长期意义以及动态状态应该去哪里读取。

## 项目状态记忆

项目状态记忆的具体整理规则见 [projects.md](projects.md)。它负责频繁变化的项目阶段和恢复入口，使 Long-term Memory 能保持相对稳定。

## 写作原则

Memory 优先使用自然语言和完整上下文，通过文档本身的章节与脉络形成结构。Short 使用统一索引加高密度正文；Long-term Memory 使用完整可读的长期文档；项目状态使用面向恢复工作的项目级组织。检索字段、图关系和机器索引由系统层派生。
