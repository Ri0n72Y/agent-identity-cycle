# Skill 与 Reference 写作原则

Skill 和 Reference 面向高性能 LLM 使用，因此写作重点是提供足够稳定、足够清楚的任务语义，让模型能够结合实际上下文完成判断，而不是用大量机械步骤替代模型自身的推理能力。主 `SKILL.md` 承担能力入口和必要路由，Reference 负责描述某类文件中的信息应该怎样存在、怎样被理解以及在同类文件之间怎样变化；涉及不同对象之间的区分和 Reflection 路由时，应优先放在主 Skill 中统一处理，避免每一篇 Reference 重复声明整套系统边界。

Reference 应围绕当前文档实际负责的信息展开，直接说明这个对象保存什么、内容怎样写以及信息怎样在该对象内部演化。不要习惯性通过连续的“不是 X”“不负责 Y”来定义对象，也不要为了显得完整而补充与当前文件没有实际关系的边界；如果某个概念的区分已经由上层 Skill 处理，Reference 可以直接使用它而无需再次展开。

优先使用长句、自然段和完整上下文来表达信息，让模型能够看到事实之间的因果、时间和语义关系。标题、列表、代码块和少量内联索引用于帮助阅读与定位，但结构本身不应成为内容的主要载体。对 Memory、Episode、Identity 等长期文本尤其如此：机器检索需要的字段、索引和图关系可以由外部系统派生，人和 Agent 共同维护的 canonical content 应保持可读、可修改、可通过 Git 理解其历史变化。

写作必须以已经发生和已经确认的内容为基础。总结讨论过程时只提炼实际出现过的修改和结论，不为形成一个看似完整的反思而编造此前不存在的错误、理论或修改记录；当已有材料无法支持某个结论时，应让该部分保持未定，而不是用合理化推断填满空缺。

Skill 的复杂度随着真实使用增长。主 `SKILL.md` 保持为稳定入口，当某条内部流程已经复杂到需要独立加载时，再增加 `workflows/` 或其他具体资源；Reference、Workflow、Script 等资源只有在存在明确运行价值时才新增，不预先建立空目录或完整模板。当前社区 Agent Skills 规范要求 Skill 至少包含 `SKILL.md`，并允许 `references/`、`scripts/`、`assets/` 以及其他附加目录按需扩展，因此这一组织方式可以保持兼容，同时给 Reflection 后续形成内部子路由留出空间。

这套原则本身也属于可演化的 Procedural Knowledge。后续真实 Agent 实践如果反复暴露新的写作问题，可以直接修改本文和对应 Skill，并通过 Git 历史保留为什么发生变化，而不把一次性的偏好或单次失败立即提升成普遍规则。
